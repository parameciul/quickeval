# server/AGENTS.md

The API. The root `AGENTS.md` holds the project-wide rules.

## Structure

- `routes/`: HTTP. `admin.ts` and its parts, `upload.ts` for students, `runner.ts` for the robot.
- `db/`: D1 queries. `lifecycle.ts` starts, schedules, promotes, and ends evaluations, and regrades; `links.ts` holds the student writes; `runner.ts` holds the robot's queries; `evaluations.ts` reads graded results and holds the teacher's corrections (`flagCountSql` counts the items to check the same way everywhere).
- `auth/`: the teacher login (`teacherAuth.ts`: the session cookie of `session.ts`, the development login, `adminOnly`), and `robotAuth.ts` for the robot key. `routes/auth.ts` is `/api/auth` (sign-up, the email confirmation, login, logout: no login needed, same-origin writes). `routes/accounts.ts` holds the teacher's own password and the administrators' accounts list. `db/accounts.ts` holds their queries; `passwords.ts` the password hashes; `email.ts` the emails (Brevo).
- `http.ts` (JSON bodies, ids, codes, same-origin writes, the `promoteDue` middleware, which runs `promoteDueTests` and starts the robot when that started an evaluation), `errors.ts` (`ApiError`), `uploads.ts` (file bodies in and out of R2), `secrets.ts` (tokens, keys, and hashes), `dispatch.ts` ("Evaluate now": GitHub's repository_dispatch).
- `test/`: the API test helper (`testApi.ts`) and fixtures.

## Rules

- Student calls are scoped by the test of the link's token, and an upload by the hash of the phone's secret (`X-Upload-Session`) within that test. Only hashes of secrets are stored.
- Each student write checks its own rules inside its SQL statement (`db/links.ts`: the test is open and its scheduled time has not come, the upload is not sent yet, at most 20 files; confirm is one `db.batch()`). Never turn these into a check before the write: two requests at once would get past it. Starting an upload still checks the open test in its route (`routes/upload.ts`), before `createSubmission` inserts (see `docs/superpowers/plans/plan-3a-followups.md`); the insert itself checks that the student is active in the test's class.
- A student write also names the phone: `OPEN_UPLOAD`, confirm and the result link check `session_hash` next to the upload's id in their SQL. Ids of deleted uploads come back, so a request that began before a reset must not land in the next upload with that id (`openSession` gives the hash to each write).
- The same holds for the robot (`db/runner.ts`): a claim, an exercise list, and a result check the lease or the run inside their SQL. `/check` and `/lease` send uploads left in grading by a dead run back to the queue. An exercise list is saved only while the test's `files_version` is the one the robot read before the files. A run never claims again an upload that a reopen took from it (`reopenTest` keeps that run's id): the next run grades it.
- The robot names what it works on, because ids of deleted rows come back: a claim returns the upload's `startedAt`, and the result (`GRADED_BY_RUN`, `failGrading`) checks it in SQL; a test read and a print job return `createdAt`, and the exercise list and the print (`WAITS_FOR_LIST`, `WAITS_FOR_PRINT`) check it. An older robot sends none: the bodies take it as optional, and the route then uses the row as it is.
- The robot's key and the settings in `routes/settings.ts` are shared by every teacher, and the key opens the robot API for all of them: only administrators (`teachers.role = 'admin'`) see or change them.
- Accounts: a sign-up inserts a `pending`, demo teacher whose email is not confirmed (`confirm_token_hash`, `email_confirmed_at`), and the insert itself checks that fewer than 50 wait and fewer than 3 came from the same IP (`signup_ip_hash`, the /64 for IPv6: `clientIpKey` in `http.ts`) in a day; accounts that waited 30 days, or were not confirmed in a day, go in the same batch, and so does an unconfirmed account of the same email (whoever owns the email can always ask again). The link in the email (`POST /api/auth/confirm`) confirms it; only then do the administrators get an email, see it on Setări, and may approve it (checked in the approve's SQL). Sign-up answers 503 `signup_off` without an email setting: nobody could confirm. A sign-up with a taken email answers 201 and changes nothing, and a locked account answers like a wrong password: the forms never tell which emails have an account. Emails go out after the answer (`inBackground` in `http.ts`), so the answer's time tells nothing either. A new password may not be one of `isCommonPassword` (`shared/accounts.ts`). An administrator sets only a teacher's password, never another administrator's (`teachersOnly`), and the teacher gets an email. Approving (`pending → active`), refusing (deletes pending rows only, one or all the page shows), and an administrator's changes (only `role = 'teacher'` rows that are not pending) check their state in their SQL. A refused account's id comes back for the next sign-up, so approving and refusing also name the account by `createdAt` (`ShownAccount` in `db/accounts.ts`), checked in their SQL. Closing an account or a new password deletes its sessions in the same batch. Only the SHA-256 of a session token is stored.
- The login lock: `takeLoginAttempt` counts the attempt and checks the lock in one UPDATE before the password is checked, so a burst of attempts at once gets at most `MAX_FAILED_LOGINS` tries; a good password starts the count again. A browser with a `qe_device` mark of the same account (`takeDeviceAttempt`, table `trusted_devices`) skips the account's lock and counts its own wrong passwords; its good login does not lift the account's lock. An unknown email, and an account without a password, still run the full hash (`verifyPassword` with no stored value), so they answer as slowly as a wrong password. A good password of a pending or closed account starts the count again. Across accounts, one IP gets at most `MAX_IP_FAILED_LOGINS` attempts in 15 minutes (`takeIpAttempt`, table `login_ips`, counted before the password like the account's; a good password takes its attempt back); a known browser skips this too. The current password on "Contul meu" counts as an attempt of the account (`takePasswordCheck`).
- The demo limit is checked inside every write that starts an evaluation (`WITHIN_DEMO_LIMIT` in `db/lifecycle.ts`: Start evaluation now, the selected uploads, the schedule, and `promoteDueTests`, whose check also counts the earlier due tests of the same teacher, because one UPDATE reads its WHERE before it writes). The trigger `tests_count_evaluation` counts a test when it goes from `open` to `evaluating`, whatever path did it, once for each `files_version` (`tests.counted_files_version`): a reopen and a new start with the same files is free, but new files make it count again, so one test cannot grade test after new test. A regrade (`done → evaluating`) grades the same uploads and is not counted or checked.
- The robot reads an open test only while it is a print job (`NEEDS_PRINT` in `db/runner.ts`), checked in SQL, and the print PDF is stored only with the run's lease and the current `files_version`.
- The teacher's corrections and Regrade check in their SQL that the upload is graded and the test is the teacher's: a regrade can delete a result at any time. A correction and the check of unreadable pages name the result the page shows: the upload in the path, and the grading time `gradedAt` (`evaluations.created_at`) in the body. Their writes check both (`SHOWN` in `db/evaluations.ts`): ids of deleted rows come back (no `AUTOINCREMENT`), so an id from an old page can name another student's upload or item. Regrade of one upload names `gradedAt` too (`regradeSubmission` in `db/lifecycle.ts`). Every action on one upload that does not name a grading names the upload by the time it started instead: Reset, Retry, publishing or taking back a result page, and the result link send `startedAt` (`submissions.started_at`, written once, so it never changes during one upload's life and differs between two uploads that reused an id). The write checks it in its SQL (`ShownUpload` in `db/submissions.ts`); a route first calls `requireShown`, which answers 404 for an unknown upload and 409 `upload_changed` for another one. A correction sums the total again from all items, so two corrections at once leave the right total. The grade comes from `gradeSql`, which a test compares with `gradeOf` for every amount in cents.
- The class analysis follows the same rules (`db/runner.ts`: `saveAnalysis`, `failAnalysis`). The robot reads the grades with a `version` (`gradesVersionSql`: the number of graded results and the time of the last change) and sends it back; the save computes the version again in its SQL, so an analysis made from grades that a correction changed meanwhile is saved with `analysis_stale = 1`. It is saved only while no upload waits for grading. Every path that makes work for the robot must start it (the schedule does not fire): "Regenerează" does, and `finishTests` waits for a requested analysis only when a graded upload exists.
- Student names are unique in a class by one key: the cleaned name (`cleanStudentName`) with letters folded to one case, the Romanian letters Ă Â Î Ș Ț included (SQLite `lower()` folds ASCII only) and the cedilla forms Ş Ţ read as Ș Ț. The JS and SQL keys must agree on every letter. Adding and renaming check the key inside their SQL statement (409 `student_exists`); students who left count; diacritics count. A list with one duplicate adds nothing. There is no UNIQUE index: the live database already holds duplicates.
- Deleting a student from a class (`DELETE /classes/:id/students/:studentId`) checks in its SQL that no upload of the student in this class's tests is `submitted`, `grading` or `graded`. It deletes this class's enrollment and the student's `uploading` and `failed` uploads there (and their R2 files), never the `students` row: `addStudentsToClass` takes `MAX(id) + 1`, so a deleted row would hand its id to the next student, and a stale page names a student by id. When a guard `EXISTS` reads a row that the same batch deletes, the guarded statement runs first.
- A test is archived (`tests.archived`, migration 0013) only while it is `done`. The archive write checks `status = 'done'` in its SQL, and every status change away from `done` (Start, Reopen, Recorectează tot, the regrade or retry of one upload, Regenerează) sets `archived = 0` in its own UPDATE. Archiving does not touch published results.
- Payments (`routes/payments.ts`, `db/payments.ts`, `payments/stripe.ts`, `docs/payments.md`): the price comes only from `PAID_FEATURES`, never from the browser. Only the signed webhook marks a payment paid, in one UPDATE that checks the status, the amount and the currency. A paid row keeps the session's `stripe_payment_intent`. Refunds and disputes (`charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`) go into `stripe_charges` by payment intent, also before the paid session arrives, with writes that are safe to repeat and to get in any order (the refunded total only grows, a closed dispute stays closed, another currency is not kept); the reads join it by payment intent and currency (`HELD` and `GIVEN_BACK` in `db/payments.ts`). A full refund or an open or lost dispute closes the feature; a partial refund keeps it; a won dispute opens it again. A new payment's INSERT checks in its SQL that the payer has no paid payment that was not given back (a full refund, a dispute closed other than won) and no open page for the same feature and test (and, for a student, that the phone's upload exists). A paid feature's route calls `requirePaid`, which takes the scope from the catalog. A student payer is named by `student_id`, a test by its id and `created_at`; student features are for one test only, because students have no login.
- The database is the truth: R2 keys come from rows, never from listing R2.
- Functions do no heavy CPU work (10 ms of CPU per request on the free plan) and make at most 15 D1 queries per request. Adding students uses a fixed number of queries, whatever the number of names; the uploads table is one query.

## Gotchas

- Local login: `.dev.vars` sets `DEV_TEACHER_EMAIL`. The API accepts it only for requests to localhost or 127.0.0.1, and only for an active account. Without it, the local app shows the login page (set a password with `npm run set-password -- <email> --local`).
- API tests: the test teacher is an administrator; `api.addTeacher(email, name, { role, demo })` adds others. A test with `env: { DEV_TEACHER_EMAIL: undefined }` logs in through `/api/auth/login` and sends the cookie (`server/routes/auth.test.ts`). `startTestApi({ app: { sendEmail } })` replaces the emails.
- API tests use wrangler's `getPlatformProxy` (`test/testApi.ts`). Do not add `miniflare` as a direct dependency: its newest version changed its options format.
- `getPlatformProxy`'s R2 refuses a request-body stream ("must have a known length"). The API reads an upload with `arrayBuffer()` (after checking `Content-Length` ≤ 25 MB) and stores the bytes; production works the same way.
- In an API test, a test set straight to `evaluating` with no upload `submitted` or `grading` turns `done` on the next request: every request ends the tests that have nothing left to grade. Add a waiting upload first.
- API tests may fake the clock with `vi.useFakeTimers({ toFake: ['Date'] })`: only Node's clock changes, and the local engine keeps working. `startTestApi({ app: { dispatchRobot } })` replaces the GitHub call; `setRobotKey()` and `robotRequest()` in `test/fixtures.ts` call the robot API.
