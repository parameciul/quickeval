# server/AGENTS.md

The API. The root `AGENTS.md` holds the project-wide rules.

## Structure

- `routes/`: HTTP. `admin.ts` and its parts, `upload.ts` for students, `runner.ts` for the robot, `quickTry.ts` for Quick Try (`/api/try`: a new try with Turnstile and the limits, and the try's link, which mounts `testRoutes` and `submissionRoutes` for the try's guest teacher behind the `ALLOWED` list; `db/quickTry.ts` holds its queries, `turnstile.ts` the Turnstile check).
- `db/`: D1 queries. `lifecycle.ts` starts, schedules, promotes, and ends evaluations, and regrades; `links.ts` holds the student writes; `runner.ts` holds the robot's queries; `evaluations.ts` reads graded results and holds the teacher's corrections (`flagCountSql` counts the items to check the same way everywhere; `listUploads` in `tests.ts` lists them per paper as `reviewPoints` by the same rule, in the same batch as the uploads).
- `auth/`: the teacher login (`teacherAuth.ts`: the session cookie of `session.ts`, the development login, `adminOnly`), and `robotAuth.ts` for the robot key. `routes/auth.ts` is `/api/auth` (sign-up, the email confirmation, login, the password reset by email, logout: no login needed, same-origin writes). `routes/accounts.ts` holds the teacher's own password and the administrators' accounts list. `db/accounts.ts` holds their queries; `passwords.ts` the password hashes; `email.ts` the emails (Brevo).
- `http.ts` (JSON bodies, ids, codes, same-origin writes, the `promoteDue` middleware, which runs `promoteDueTests` and starts the robot when that started an evaluation), `errors.ts` (`ApiError`), `uploads.ts` (file bodies in and out of R2), `secrets.ts` (tokens, keys, and hashes), `dispatch.ts` ("Evaluate now": GitHub's repository_dispatch).
- `test/`: the API test helper (`testApi.ts`) and fixtures.

## Rules

- Student calls are scoped by the test of the link's token, and an upload by the hash of the phone's secret (`X-Upload-Session`) within that test. Only hashes of secrets are stored.
- Each student write checks its own rules inside its SQL statement (`db/links.ts`: the test is open and its scheduled time has not come, the upload is not sent yet, at most 20 files; confirm is one `db.batch()`). Never turn these into a check before the write: two requests at once would get past it. Starting an upload still checks the open test in its route (`routes/upload.ts`), before `createSubmission` inserts (see `docs/superpowers/plans/plan-3a-followups.md`); the insert itself checks that the student is active in the test's class.
- A student who leaves a name ("Alege alt nume") gives it back: `DELETE /api/u/:token/sessions` (`releaseSubmission`) deletes the phone's upload only while it is `uploading` and has no file, checked in its SQL. An upload with files, or one not tied to the phone's secret, stays; the teacher unlocks it ("Deblochează" / "Șterge și deblochează" on the uploads table, which call Reset). Closing the page releases nothing.
- A student write also names the phone: `OPEN_UPLOAD`, confirm and the result link check `session_hash` next to the upload's id in their SQL. Ids of deleted uploads come back, so a request that began before a reset must not land in the next upload with that id (`openSession` gives the hash to each write).
- The same holds for the robot (`db/runner.ts`): a claim, an exercise list, and a result check the lease or the run inside their SQL. `/check` and `/lease` send uploads left in grading by a dead run back to the queue. An exercise list is saved only while the test's `files_version` is the one the robot read before the files. A run never claims again an upload that a reopen took from it (`reopenTest` keeps that run's id): the next run grades it.
- The robot names what it works on, because ids of deleted rows come back: a claim returns the upload's `startedAt`, and the result (`GRADED_BY_RUN`, `failGrading`) checks it in SQL; a test read and a print job return `createdAt`, and the exercise list and the print (`WAITS_FOR_LIST`, `WAITS_FOR_PRINT`) check it. An older robot sends none: the bodies take it as optional, and the route then uses the row as it is.
- The robot's key and the settings in `routes/settings.ts` are shared by every teacher, and the key opens the robot API for all of them: only administrators (`teachers.role = 'admin'`) see or change them. A new key's time is kept beside its hash, in the same batch (`runner_key_at`, `Settings.robotKeyAt`).
- Accounts: a sign-up inserts a `pending`, demo teacher whose email is not confirmed (`confirm_token_hash`, `email_confirmed_at`). Every sign-up request counts in `signup_ips` (the IP's key from `clientIpKey` in `http.ts`: the /64 for IPv6), whatever its outcome, so the limits tell nothing about the email: at most `MAX_SIGNUPS_PER_IP` a day from one IP and `MAX_SIGNUPS_PER_DAY` from all (each IP adds at most its own limit to the total, so one IP cannot close sign-ups; spreading over many IPv6 /64s can, an accepted limit), and at most 50 confirmed accounts wait; the insert checks all of it in its SQL. Accounts that waited 30 days, or were not confirmed in a day, go in the same batch, and so does an unconfirmed account of the same email once `RESEND_MINUTES` passed from the IP that asked (`confirm_ip_hash`), or `REPLACE_MINUTES` from another (whoever owns the email can ask again, an email gets at most one link in that time, and nobody else can keep cancelling the link). The link (`POST /api/auth/confirm`) confirms only with the password chosen at the sign-up, so someone who asks with another person's email cannot get that person to confirm it; only then do the administrators get an email, see it on Setări, and may approve it (checked in the approve's SQL). Sign-up answers 503 `signup_off` without an email setting: nobody could confirm. A sign-up with a taken email answers 201 and changes nothing, and a locked account answers like a wrong password: the forms never tell which emails have an account. Emails go out after the answer (`inBackground` in `http.ts`), so the answer's time tells nothing either. A new password may not be one of `isCommonPassword` (`shared/accounts.ts`). An administrator sets only a teacher's password, never another administrator's (`teachersOnly`), and the teacher gets an email. Approving (`pending → active`), refusing (deletes pending rows only, one or all the page shows), and an administrator's changes (only `role = 'teacher'` rows that are not pending) check their state in their SQL. A refused account's id comes back for the next sign-up, so approving and refusing also name the account by `createdAt` (`ShownAccount` in `db/accounts.ts`), checked in their SQL. Closing an account or a new password deletes its sessions in the same batch. Only the SHA-256 of a session token is stored. An account's history (`account_events`, migration 0028) writes itself from triggers on `teachers`, whatever the path (the command line included): created, email confirmed and approved take the row's own times, demo, complete, closed, reopened and password the time of the change; a Quick Try's guest teacher has none. Every write that an administrator or the teacher makes sets `teachers.changed_by` first, and the trigger copies it into `account_events.by_teacher_id`, so the page says who approved, changed or closed an account; the email confirmation, the reset link and the command line name no one. A refused request leaves a row in `refused_accounts` (who asked, when, and who refused), written in the same batch and under the same guard as its delete, so a refusal that matched nothing writes nothing. The same migration counts the robot work outside grading in `teachers.barems_generated`, `exercise_lists_made`, `analyses_made` and `prints_made`, through triggers on `tests` (the class and CES variants together; a work the robot gave up on counts nothing), and the last good login in `teachers.last_login_at` (`createSession`), which outlives its sessions. The robot work, grading included, is one row per operation in `robot_work` (migration 0029: teacher, test, kind, variant, ok, tokens, at), which `logRobotWork` (`db/runner.ts`) writes after each save and each failure but a usage limit; the teacher comes from the test, so a test deleted at that moment logs nothing. `GET /api/admin/accounts/:id` ("Detalii" on Setări) reads one account with its events and who made them, what it made, the grading of the last 30 days and the room its papers take, the robot work by kind and by test with the tokens, and each test; `GET /api/admin/accounts/refused` lists the newest 50 refused requests. Both stay within 15 D1 queries; a guest teacher is no account (404).
- The login lock: `takeLoginAttempt` counts the attempt of the account and of the IP, and checks both, in one batch before the password is checked (one round trip whatever the email, so the time tells nothing), so a burst of attempts at once gets at most `MAX_FAILED_LOGINS` tries; a good password starts the account's count again. The IP (table `login_ips`) keeps every attempt but a good password (an unknown email and a locked account count too, so the count tells nothing about the email). Past `MAX_IP_FAILED_LOGINS` in 15 minutes the IP gets 429 `network_blocked`, with its own message: a school's teachers share one IP. A browser with a `qe_device` mark of the same account (`takeDeviceAttempt`, table `trusted_devices`) skips the account's lock and the IP's limit and counts its own wrong passwords; its good login does not lift the account's lock. An unknown email, and an account without a password, still run the full hash (`verifyPassword` with no stored value), so they answer as slowly as a wrong password. A good password of a pending or closed account starts the count again. The current password on "Contul meu" counts as an attempt of the account (`takePasswordCheck`).
- Password reset (`POST /api/auth/forgot-password`, `/reset-password`; migration 0023): an active account gets a link by email (`requestPasswordReset`: `reset_token_hash`, one hour, once), at most one every `RESET_RESEND_MINUTES` and `MAX_RESETS_PER_ACCOUNT` a day (`reset_count`), checked in the SQL, so nobody can flood an inbox or keep replacing the link; every request counts in `reset_ips` (`MAX_RESETS_PER_IP` a day), whatever the email, and the answer is the same for any email, sent before the email goes out. The link is after `#` (`/teacher/parola-noua#<token>`). `resetPassword` checks the token and its expiry in its SQL, ends every login of the account, lifts its lock and deletes its known browsers (`trusted_devices`); `resetLinkWorks` reads the link first, so a made-up link costs no password hash. `setPassword` and closing an account also drop a pending link. Off (503 `reset_off`) without an email setting.
- Class analysis: entering evaluation does not ask for it (`ASK_FOR_ANALYSIS` drops a ready or failed one to `none`). `askForAnalysis` runs before every `finishTests` and asks for it when the test is in evaluation, nothing waits for grading, a paper is graded and `flagCountSql` sums to 0; `askAnalysisAfterCheck` does the same after the teacher's check (item or unreadable pages), also for a `done` test, which goes back to evaluation, and the route starts the robot. A ready analysis is never asked for again by a check: "Regenerează" does that.
- Evaluations: the trigger `tests_count_evaluation` adds one to `teachers.tests_evaluated`, for every teacher, each time a test moves into `evaluating` with uploads waiting for grading: every start (now, the selected uploads, a scheduled one), and a regrade or retry that sends a finished test back. A regrade or retry on a test that was in evaluation already counts too (`countGradingAgain`, a statement after the batch, when the regrade's UPDATE returned rows with that status from before the batch). "Regenerează" (only the analysis) and a test with nothing to grade do not count. The trigger `submissions_count_paper` (migration 0019) adds one to `teachers.papers_graded`, for every teacher, each time a paper (one student's whole upload) becomes `graded`: a regrade counts as one more, a failed grading as none. A demo account may have one test graded and `DEMO_PAPER_LIMIT` papers graded in total (`ONLY_TEST` in `WITHIN_PAPER_LIMIT` refuses a start, schedule or due start when another test of the teacher was sent to the robot; `papersToSend` sends the papers of the first test only; a regrade or retry is not checked for it; `teachers.graded_test_id` (migration 0021, set by a trigger when a paper is first graded) keeps the place when papers are reset; a test deleted after its grading frees it unless its id is reused, the paper limit still holds; a due test the rule keeps out loses its schedule in `promoteStatements`, and a second schedule is refused), and the papers on their way to the robot use the limit too (`papersLeft` in `db/lifecycle.ts`; `papersWaitingSql` gives the page the same count), checked inside each of those writes: with no paper left a start, a schedule, a regrade or a retry changes nothing (`WITHIN_PAPER_LIMIT`, `MAY_GRADE_AGAIN`), and the route says so only when the limit was the reason (`regradeBlockedByDemoLimit`). With some left, a start sends the first papers (`papersToSend`: by scheduled time and test, then the confirmed ones, oldest first), and the others go back to `uploading` as unselected uploads do, so the test page shows "Evaluare parțială". Due tests of one teacher share the papers left, in that order; a due test with no paper within the limit stays open, as it was (`STARTS`). "Recorectează tot" sends the papers left, the failed ones first, and the others keep their results; its `count` says how many went. A regrade of an open test also counts the papers that wait in that test, because they would take the places at its next start.
- A generated barem (`tests.barem_request`, `barem_unchecked`): `BAREM_ACTIVE` in `db/lifecycle.ts` is in the SQL of every path that moves an open test into evaluation (start now, the selected uploads, schedule, the scheduled `DUE`), so an unchecked or still generating barem never grades. Regrade and retry do not need it: they start from `done`, and a barem becomes unchecked or requested only in draft or open. The robot's `barem` job is saved only with the run's lease and the current `files_version`; "Am verificat baremul" names the `filesVersion` the page showed.
- The robot reads a draft or open test only while it is a print job (`NEEDS_PRINT` in `db/runner.ts`), checked in SQL, and the print PDF is stored only with the run's lease and the current `files_version`.
- The CES variant (migration 0024): every column of the test file, the barem, its comments and request, the exercise list and the print PDF has a `ces_` twin, with its own `ces_files_version`; the queries that serve both take a `variant` and name their columns with `columns(variant)` (`db/variant.ts`, also `needsPrintSql`, `needsBaremSql`, `baremActiveSql`, `paperVariantSql`). The teacher's CES routes are `/api/admin/tests/:code/ces/…` (`routes/cesVariant.ts`); a CES file or comment change is refused only while a CES paper is in grading, and a CES barem may be generated until the test is done. The robot's routes take `?variant=ces` (none: the class test, as an older robot asks); `/tasks` lists `cesPrints`, `cesBarems` and `cesExerciseLists`. The CES list waits for an active CES barem, the class list and a CES paper (`NEEDS_CES_EXERCISE_LIST`). `GRADABLE` holds a CES paper back until its CES barem is active and its CES list usable, and the claim checks it again and writes `submissions.variant` in the same UPDATE; `findGrading` checks a result against the list of the paper's variant. "Șterge varianta CES" (`removeCesVariant`) checks in its SQL that no paper has the variant `ces`. The CES switch (migration 0025, `tests.ces_off`, stored as "off" so that every test asks for the CES files until the teacher says no): Test nou sends `cesOff`; `PUT /:code/ces/off` (`setCesOff`) turns it off in the same guarded write as the removal (and starts the robot during the evaluation), or on; a CES file sets `ces_off = 0` in its own UPDATE. `TestSummary.prepared.ces` gives the tests list what the CES variant has (`wanted`: an active CES student and the switch on). The CES barem job (`needsBaremSql('ces')`) waits while the class barem is being generated. The report gives the CES columns apart (`cesExercises`) only when they are not the class ones (`sameExercises` in `shared/stats.ts`); the class analysis gets each paper's `variant` and the CES exercises.
- A test gets its `upload_token` in its INSERT (`createTest`), so a draft has its print PDF; Start test keeps it (`COALESCE`, for a draft made before that). A draft made before that gets one at Start, with a new test file (`saveTestFile`), or with "Pregătește testul cu cod QR" (`retryPrint`). Stop test (`stopTest`: open → draft, clears `started_at` and `evaluation_at`) checks in its SQL that the test was never evaluated (`evaluation_started_at IS NULL`) and that no upload of the test has a file or is past `uploading` (`NO_STUDENT_FILES`); a student file that lands at the same moment checks the open test in its own SQL (`OPEN_UPLOAD`), so one of the two is refused. Student writes on a draft answer 409 `not_started`.
- "Marchează ca terminat" (`finishOpenTest`, `POST /:code/finish`): an open test (reopened after its grading) becomes `done` with no robot and no count, only when a paper is graded and no paper waits (sent, in grading, or uploaded with files), checked in its SQL. The class analysis is left as it is; a requested one becomes `none`, as in `finishTests`.
- The teacher's corrections and Regrade check in their SQL that the upload is graded and the test is the teacher's: a regrade can delete a result at any time. A correction and the check of unreadable pages name the result the page shows: the upload in the path, and the grading time `gradedAt` (`evaluations.created_at`) in the body. Their writes check both (`SHOWN` in `db/evaluations.ts`): ids of deleted rows come back (no `AUTOINCREMENT`), so an id from an old page can name another student's upload or item. Regrade of one upload names `gradedAt` too (`regradeSubmission` in `db/lifecycle.ts`). Every action on one upload that does not name a grading names the upload by the time it started instead: Reset, Retry, publishing or taking back a result page, and the result link send `startedAt` (`submissions.started_at`, written once, so it never changes during one upload's life and differs between two uploads that reused an id). The write checks it in its SQL (`ShownUpload` in `db/submissions.ts`); a route first calls `requireShown`, which answers 404 for an unknown upload and 409 `upload_changed` for another one. A correction sums the total again from all items, so two corrections at once leave the right total. The grade comes from `gradeSql`, which a test compares with `gradeOf` for every amount in cents.
- The class analysis follows the same rules (`db/runner.ts`: `saveAnalysis`, `failAnalysis`). The robot reads the grades with a `version` (`gradesVersionSql`: the number of graded results and the time of the last change) and sends it back; the save computes the version again in its SQL, so an analysis made from grades that a correction changed meanwhile is saved with `analysis_stale = 1`. It is saved only while no upload waits for grading. Every path that makes work for the robot must start it (the schedule does not fire): "Regenerează" does, and `finishTests` waits for a requested analysis only when a graded upload exists.
- Student names are unique in a class by one key: the cleaned name (`cleanStudentName`) with letters folded to one case, the Romanian letters Ă Â Î Ș Ț included (SQLite `lower()` folds ASCII only) and the cedilla forms Ş Ţ read as Ș Ț. The JS and SQL keys must agree on every letter. Adding and renaming check the key inside their SQL statement (409 `student_exists`); students who left count; diacritics count. A list with one duplicate adds nothing. There is no UNIQUE index: the live database already holds duplicates. An archived class takes no new students (409 `class_archived`, `archived = 0` in the INSERT's `EXISTS`) and no new test (`createTest`).
- The student's history (`getStudentHistory`, one batch of four statements) lists the started tests of the student's classes; an archived test, or a test of a class the student left, only when the student sent a paper to it. Its papers use the grades table's columns (`GRADE_COLUMNS` and `gradeOf` in `db/students.ts`, shared with `listClassGrades`).
- Search (`routes/search.ts`, `db/search.ts`, `GET /api/admin/search?q=&year=`): the students of the year's classes (one batch of two statements: their enrollments, with the classes they are in or the ones they left when they are in none, and a window query for the grade of each one's latest graded paper of the year), the year's classes (`listClasses`) and its tests (`listTests`, the Teste page's rows) are read whole, at once, and matched in the Worker with `searchMatcher` of `shared/search.ts` (NFD, no marks, one case). No folded column: one teacher has a few hundred names in a year, and SQLite's `LIKE` folds only ASCII. A class matches by its stored name ("10B"), not by "Clasa 10B". The search needs two letters once folded and at most 80 characters (400 otherwise); a test counts the queries of one request against the 15 allowed.
- Deleting a student from a class (`DELETE /classes/:id/students/:studentId`) checks in its SQL that no upload of the student in this class's tests is `submitted`, `grading` or `graded`. It deletes this class's enrollment and the student's `uploading` and `failed` uploads there (and their R2 files), never the `students` row: `addStudentsToClass` takes `MAX(id) + 1`, so a deleted row would hand its id to the next student, and a stale page names a student by id. When a guard `EXISTS` reads a row that the same batch deletes, the guarded statement runs first.
- A test is archived (`tests.archived`, migration 0013) only while it is `done`. The archive write checks `status = 'done'` in its SQL, and every status change away from `done` (Start, Reopen, Recorectează tot, the regrade or retry of one upload, Regenerează) sets `archived = 0` in its own UPDATE. Archiving closes every result page of the test (`tests.results_open` and `submissions.results_open`, in the same batch, after the archive's UPDATE, checked by `archived = 1`, so a refused archive closes nothing); taking it out of the archive opens nothing. The teacher may publish on an archived test ("De făcut" then shows it). Archiving a class (`updateClass` with `archived: true`) closes the result pages of all its tests the same way, and archives none of them.
- Payments (`routes/payments.ts`, `db/payments.ts`, `payments/stripe.ts`, `docs/payments.md`): the price comes only from `PAID_FEATURES`, never from the browser. Only the signed webhook marks a payment paid, in one UPDATE that checks the status, the amount and the currency. A paid row keeps the session's `stripe_payment_intent`. Refunds and disputes (`charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`) go into `stripe_charges` by payment intent, also before the paid session arrives, with writes that are safe to repeat and to get in any order (the refunded total only grows, a closed dispute stays closed, another currency is not kept); the reads join it by payment intent and currency (`HELD` and `GIVEN_BACK` in `db/payments.ts`). A full refund or an open or lost dispute closes the feature; a partial refund keeps it; a won dispute opens it again. A new payment's INSERT checks in its SQL that the payer has no paid payment that was not given back (a full refund, a dispute closed other than won) and no open page for the same feature and test (and, for a student, that the phone's upload exists). A paid feature's route calls `requirePaid`, which takes the scope from the catalog. A student payer is named by `student_id`, a test by its id and `created_at`; student features are for one test only, because students have no login.
- The database is the truth: R2 keys come from rows, never from listing R2.
- Functions do no heavy CPU work (10 ms of CPU per request on the free plan) and make at most 15 D1 queries per request. Adding students uses a fixed number of queries, whatever the number of names; the uploads table is one batch of two queries (the rows, and the points to check).

## Gotchas

- Local login: `.dev.vars` sets `DEV_TEACHER_EMAIL`. The API accepts it only for requests to localhost or 127.0.0.1, and only for an active account. Without it, the local app shows the login page (set a password with `npm run set-password -- <email> --local`).
- API tests: the test teacher is an administrator; `api.addTeacher(email, name, { role, demo })` adds others. A test with `env: { DEV_TEACHER_EMAIL: undefined }` logs in through `/api/auth/login` and sends the cookie (`server/routes/auth.test.ts`). `startTestApi({ app: { sendEmail } })` replaces the emails.
- API tests use wrangler's `getPlatformProxy` (`test/testApi.ts`). Do not add `miniflare` as a direct dependency: its newest version changed its options format.
- `getPlatformProxy`'s R2 refuses a request-body stream ("must have a known length"). The API reads an upload with `arrayBuffer()` (after checking `Content-Length` ≤ 25 MB) and stores the bytes; production works the same way.
- In an API test, a test set straight to `evaluating` with no upload `submitted` or `grading` turns `done` on the next request: every request ends the tests that have nothing left to grade. Add a waiting upload first.
- API tests may fake the clock with `vi.useFakeTimers({ toFake: ['Date'] })`: only Node's clock changes, and the local engine keeps working. `startTestApi({ app: { dispatchRobot } })` replaces the GitHub call; `setRobotKey()` and `robotRequest()` in `test/fixtures.ts` call the robot API.
